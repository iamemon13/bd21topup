# Phase 2 dry-run dispatch foundation

The dispatch queue is independent of `orders.status` and every financial table. The API accepts only `orderId`, derives the authenticated administrator from the bearer session, reloads the order, package, and complete wallet evidence, then calls an atomic database function. Package UUID, name, category, mapping version, and ordered structured operations are checked again in PostgreSQL.

`topup_dispatches` has one row per order and mapping version. `topup_dispatch_operations` stores product code, quantity, sequence, and command hash; plaintext supplier commands and credentials are not stored. A unique dispatch constraint makes retries and page refreshes reuse the same record. Per-dispatch sequence and operation-key constraints keep operations stable.

The dry-run worker claims one operation atomically with `FOR UPDATE SKIP LOCKED`. Later bundle operations stay blocked until earlier operations reach `dry_run_completed`. Before transport, it persists a unique send intent in a separate atomic transition. A stale claim with no send intent can safely return to `queued`; a stale operation with durable send intent moves to `manual_review` and can never be reclaimed for a blind resend. Any transport exception also becomes `manual_review`.

Every operation hash is independently recomputed in PostgreSQL from the mapping version, UID, sequence number, product code, and quantity. The service role has read-only access to dispatch tables and can change state only through fixed-path `SECURITY DEFINER` functions. Each claim, send-intent, completion, and recovery transition writes its audit row in the same transaction, so an audit failure rolls back the state change.

An existing dispatch is reusable only while its immutable snapshots, payment evidence ID, ordered operation manifest, and hashes still match the current order, package, and complete wallet evidence. PostgreSQL repeats this validation under row locks before claim and immediately before durable send intent. A mismatch moves queued or claimed work to audited `manual_review`; the worker treats a rejected send intent as a hard stop and never calls transport.

Row locks alone cannot stop a concurrent insert for the same wallet `reference_id`. Every non-null `wallet_transactions` insert therefore passes through a `BEFORE INSERT` trigger that takes the same transaction-scoped PostgreSQL advisory lock used by authoritative dispatch validation. The key is `(1110721073, first 32 UUID bits)`: the first value reserves the BD21 order-wallet namespace, and a rare second-key collision only causes harmless extra serialization. Locks release automatically at commit or rollback. `reference_id` remains intentionally non-unique because refunds and ledger history may legitimately share a reference.

Lock order is dispatch row, order row, reference advisory lock, package row, then wallet evidence. Order cancellation already locks the order before inserting its refund, so its insert trigger cannot deadlock with Phase 2: whichever transaction owns the order lock reaches the advisory lock first. Initial wallet checkout inserts a new uncommitted order before its ledger row, so no dispatch can observe that order until both commit. A safe isolated real PostgreSQL instance was not available for a destructive two-session test; PGlite coverage verifies the shared SQL protocol but is not represented as a true concurrency test.

`DryRunTelegramTransport` is deterministic and has no network client. There is no production Telegram transport, login path, credential configuration, or order-completion path. Supplier response correlation currently fails closed unless mocked evidence includes an exact reply link, UID, and known supplier reference. Real reply formats must be collected and tested before this can be enabled.

Future real activation requires secure personal-account MTProto authentication, encrypted session handling, persistent single-purpose worker hosting, exact supplier reply fixtures, reliable correlation, monitoring and alerts, and a staffed manual-review workflow. The real transport must record send intent before I/O and must never retry an uncertain delivery automatically.
